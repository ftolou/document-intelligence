# Application use-case boundary

Flask is a transport adapter. Route functions parse HTTP input, invoke one
application use case, and present the returned result. They do not coordinate
storage, model execution, human-review persistence, or worker lifecycle.

```text
HTTP routes
    -> application use cases
        -> existing domain/application services
            -> storage and model adapters
```

The use-case registry is assembled in `web/dependencies.py` and exposes only:

- `JobUseCases`
- `ReceiptUseCases`
- `ReviewUseCases`
- `AskReceipts`
- `RuntimeUseCases`

Concrete `JobStore`, `ReceiptDatabase`, OCR engines, and processing services are
owned by the composition boundary and are not exposed to blueprints.

## Resource references

Application code does not construct `/api/...` paths. Job artifacts are returned
as transport-neutral references:

```json
{
  "resource_kind": "job_artifact",
  "job_id": "abc123",
  "filename": "approved_receipt.json"
}
```

`web/presentation.py` converts those references into HTTP URLs only when a Flask
response is produced. Historical jobs that already contain URL strings remain
readable.

## Background execution

`JobUseCases` persists a serializable `JobDispatchRequest` and submits it through
the `JobDispatcher` port. Worker capacity, recovery, claims, retries, and
lifecycle transitions belong to the dispatcher and job repository adapters, not
to Flask routes or use cases. The default bounded process-level implementation
can later be replaced by an external durable queue without changing HTTP
controllers.

## Enforcement

Run:

```bash
python scripts/check_application_boundaries.py
```

The check rejects:

- route imports of concrete storage, services, RAG-SQL, observability, or process modules;
- transport paths generated by application or service modules;
- concrete persistence resources exposed through the Flask dependency registry.
